## 0. 总体判断

设计的整体质量高于常见的 P0 规划：账号与旅行的复合外键隔离、金额十进制与币种小数位校验、幂等收据、版本化资源、文件先校验后关联、导出与永久删除的失效规则，这些都是正确且值得保留的决定。三份详细设计之间的映射基本完整，90 个接口与 26 张表可以互相对应。

主要问题集中在三类：

1. **与需求或自身矛盾的缺陷**：照片必须 ready 才能建引用与 TR-08 的上传状态需求矛盾；刷新令牌复用即撤销会话会造成确定性误登出；离线"创建后再编辑"的版本链规则自相矛盾；快照 worker 的共享锁会阻塞该账号全部写入；索引方向与接口默认排序不一致。
2. **对"个人 + AI 开发的 P0"而言过重的机制**：同步协议叠加了快照任务、跨页批次暂存、redacted、墓碑、永久收据、depends_on 等机制，其中一半可以在不损失需求的前提下去掉；文件上传一张图要 6 次调用；写操作不返回资源导致每次写后再读。
3. **尚未决定或未验证的依赖**：uni-app x 的 SQLite 只有插件市场的 UTS 插件、地图与地点选择供应商、邮件与对象存储厂商、对象存储备份、账号存储配额。

## 1. 必须修正的问题（写 OpenAPI 与迁移前定案）

### M1. 只有 ready 资产可建引用，与 TR-08 矛盾

- 位置：总览 5.1；接口设计 3.7"完整上传流程"、2.7；数据库 §16 规则。
- 问题：照片、资料、票据只能引用 status=ready 的资产，照片记录在 ready 之前不能存在。需求 TR-08 要求"显示照片上传中、已完成或失败状态，失败后可重试"。接口清单只有单个 GET /assets/{id}，没有资产列表，网页刷新或换设备后无法找回"哪张失败了"。未建引用的资产 24 小时后被当作无引用回收。
- 影响：上传状态只能存在客户端内存；安卓离线拍照并写说明时，照片记录进不了常规待同步队列，客户端需要额外维护一套文件队列。
- 建议：允许 journal_photos、documents、ledger_attachments 引用同账号同旅行的 uploading/processing/failed 资产；Photo、Document、LedgerEntry 的响应与同步快照携带资产状态摘要（status、thumbnail_status、media_type、width、height）；ready 只作为下载、缩略图与导出的条件；失败时在同一资产上创建新尝试；同步推送可增加 `photo.create`（仅元数据）。

### M2. 刷新令牌"命中前次摘要即撤销会话"造成确定性误登出

- 位置：接口设计 3.1；数据库 §2 规则"命中前次摘要时撤销该会话"、"刷新响应丢失后的旧令牌重试可能需要重新登录"。
- 问题：移动弱网下刷新响应丢失后用旧令牌重试是正常行为；网页每个标签页各持一份内存 access_token，过期时并发刷新几乎必然发生。两种情况都会被判定为令牌盗用并撤销整个会话。
- 建议：为前次令牌设置 30–60 秒宽限期，宽限期内命中前次摘要返回同一组新令牌（幂等刷新），超期再按复用撤销；网页端用 Web Locks 或 BroadcastChannel 让标签页串行刷新；令牌格式改为 `<session_id>.<secret>`，按主键定位会话后常量时间比较，previous_refresh_token_hash 无需索引（见 D5）。

### M3. 离线"创建后再编辑"的版本链规则自相矛盾

- 位置：接口设计 4.1"对同一新实体紧接着再编辑……"。
- 问题：该段要求"先合并尚未提交的创建命令"，但合并会改变同一 operation_id 的内容，若首次请求其实已落库，按 1.2 与数据库 §20 的 request_hash 规则会返回 IDEMPOTENCY_CONFLICT。同段又要求"先用原 operation_id 查询重试结果"，接口清单没有对应端点。
- 建议：操作入队后不可变，不做合并；规定本地新建实体的版本链是确定的：创建后 version=1（数据库默认值），本设备每次后续更新 +1，直到收到其他设备的变更；"查询重试结果"就是原样重发并得到 replayed=true，或补一个 `GET /sync/operations/{operation_id}` 读收据。

### M4. 快照 worker 的 FOR SHARE 会阻塞该账号全部写入

- 位置：总览 4.3；数据库 §22 规则。
- 问题：worker 在 REPEATABLE READ 事务内对 account_sync_state 取 FOR SHARE，读全部选定旅行、写 snapshot_items 与 snapshot_asset_refs，提交后才释放；业务写事务第一步就是对同一行 FOR UPDATE。baseline 或"导出全部旅行"期间，该用户在网页与安卓的所有写入排队。此外在 REPEATABLE READ 下，若该行在快照建立后被并发更新，FOR SHARE 会直接报序列化失败，写入活跃的账号会反复重试。
- 分析：这把锁对一致性没有贡献。seq 在锁内分配并随业务行同事务提交，REPEATABLE READ 事务第一条语句读到 last_seq=N 时，seq ≤ N 的事务必然全部已提交且可见，seq > N 的全部不可见，切片天然一致。锁的唯一作用是挡住并发的文件回收。
- 建议：去掉该锁。文件回收与快照的竞争由 snapshot_asset_refs 到 assets 的外键解决：回收时同事务删除 assets 行并事务入队对象删除任务，快照插入引用要么成功要么因行已删而整体重试。若采纳 S1 取消快照表，此问题随之消失。

### M5. 写事务隔离级别未写明，锁内操作无界限

- 位置：总览 4.1；后端结构 7.2；数据库 §18 规则。
- 问题："SELECT … FOR UPDATE 后重读最新行版本再排队"的语义只在 READ COMMITTED 下成立；若工程默认 REPEATABLE READ，两端并发写同一账号时后到事务直接报 could not serialize access。account_sync_state 是每账号热行，每笔写都更新它；锁内执行大批重排或分批永久删除时其它设备排队。
- 建议：总览 4.1 写死"可同步写事务使用 READ COMMITTED，概览与导出的只读事务使用 REPEATABLE READ"；取锁必须是事务第一条语句；设置 lock_timeout 与 statement_timeout；永久删除的 remove_rows 阶段每批单独取锁；account_sync_state 建表加 `WITH (fillfactor = 70)`；接受"单账号写吞吐约等于 1/事务时长"的上限。

### M6. 版本校验过严，离线最高频操作最容易冲突

- 位置：接口设计 4.1 的 packing_item.set_status、todo.set_completed 要求 base_version；数据库 §5 规则"删除或切到 skipped 时……递增这些资源版本"；§12、§14 删除预订、笔记同样递增被解除关联资源的版本。
- 问题：网页改了一件物品的备注，安卓离线勾选"已装包"就冲突；网页删除一个行程项会递增关联账目、笔记、照片、待办的版本，安卓离线改账目备注就冲突。这些冲突对用户没有意义，却要人工裁决。
- 建议：set_status 与 set_completed 无条件应用（最后写入生效，递增版本经变更流回传），版本冲突只保留给账目与笔记���文；服务端"解除关联"类修改不参与客户端版本校验，或在同步快照中增加 changed_fields 让客户端做字段级合并。

### M7. 逐文件 60 秒下载授权无法支撑网页相册与离线下载

- 位置：接口设计 2.7、3.7 DownloadAuthorization；3.1"access_token 只放内存"。
- 问题：网页 `<img src>` 无法附带 Bearer，签名 URL 是唯一途径；100 张缩略图需要 100 次授权调用；URL 每次不同，浏览器缓存失效；懒加载或停留超过 60 秒后回滚页面图片全部失效。安卓离线下载 N 个文件需要 2N 次调用。
- 建议：增加批量授权 `POST /assets/download-authorizations`（一次 ≤100 个 asset_id + variant）；缩略图 TTL 放宽到 10–15 分钟，原图与 PDF 保持短时；增加 disposition=inline/attachment 参数以支持 PDF 内联查看与 TR-07 的"下载"；original_name 进入 Content-Disposition 时按 RFC 5987 编码；签名 URL 固定 Content-Type，避免在存储域内联渲染任意内容；响应允许 `Cache-Control: private`。

### M8. 上传一张图 6 次调用加轮询

- 位置：接口设计 2.7、3.7；数据库 §16、§17。
- 问题：createAsset → createAssetUpload（If-Match）→ authorize → PUT → confirm（新版本 + 幂等键）→ 轮询 getAsset → 建引用。30 张照片约 200 次请求，资产版本中途变两次；asset_uploads 与 assets 之间还有循环外键。
- 建议：`POST /assets` 一步创建资产、首个尝试并直接返回上传授权；`POST /assets/{id}/upload-authorization` 用于重试或续签；`POST /assets/{id}/confirm` 返回资产状态；上传步骤以 upload_id 作并发标识，不用 If-Match。asset_uploads 并入 assets：P0 只允许一个活动尝试，staging_object_key、expected_size、declared_media_type、client_sha256、upload_expires_at、attempt_no 作为 assets 列，重试递增 attempt_no 生成新暂存键，旧暂存对象靠桶生命周期规则清理。`DELETE /assets/{id}` 可删除，24 小时无引用回收已覆盖。

### M9. 写操作不返回资源，每次写后再 GET

- 位置：接口设计 1.2"写操作统一返回 WriteResult"、1.4。
- 问题：服务端会写入客户端不知道的值：默认 occurred_on、recorded_on、completed_at、新行程项的 sort_order、首次记账后的 trip.currency_locked_at 与版本。客户端每次写后必须再 GET 才能刷新界面。"收据不保留正文"只约束重放响应，不要求实时响应也省略资源。
- 建议：WriteResult 增加 data（primary 的规范资源）；replayed=true 时按 id 重新读取当前态返回（可能是更新的版本），或置 null 由客户端 GET；同步推送结果同样携带 data。

### M10. 索引与接口默认排序不一致、缺尾键、可空排序键

- 位置：数据库 §10、§13、§7、§12、§14、§4、§25 的索引；接口设计 3.9 查询模型。
- 问题：
  - ledger_entries 索引 `(account_id, trip_id, occurred_on DESC, id)` 中 id 为升序，接口默认"occurred_on、id 降序"；documents 索引 `(…, created_at DESC, id)` 同样；ledger 第二个索引 `(account_id, trip_id, category, occurred_on)` 没有 id 尾键。键集分页的行比较无法直接走索引。
  - todo_items 唯一的列表索引带 `WHERE completed_at IS NULL`，但 state=all/completed 同样按 due_on 分页。
  - due_on ASC NULLS LAST、start_local NULLS LAST、recorded_on DESC NULLS LAST 三处可空排序键，键集游标必须区分"游标值为 NULL"与非 NULL 两套谓词，容易写错且索引利用差。
  - 回收站索引 `(account_id, deleted_at DESC)` 与 export_jobs `(account_id, created_at DESC)` 缺 id 尾键，同事务删除多趟旅行时 deleted_at 相同，游标无法唯一定位。
- 建议：排序方向二选一后索引与接口保持一致（推荐 `(…, occurred_on DESC, id DESC)`）；category 索引补 id；可空排序键改为表达式索引，把 NULL 映射为哨兵值，例如 `COALESCE(due_on, DATE '9999-12-31')`，ORDER BY 与 WHERE 使用同一表达式；todo 用一个 `(account_id, trip_id, <哨兵表达式>, id) WHERE deleted_at IS NULL` 覆盖四种 state；回收站与导出索引补 id。

### M11. 循环外键的删除顺序未写

- 位置：数据库 §1 累计、§16 键与关联、§26 规则。
- 问题：accounts(id, avatar_asset_id) → assets 与 assets(account_id, id, active_upload_id) → asset_uploads 都按默认 ON DELETE NO ACTION 建立，永久删除与注销的 remove_rows 阶段没有写"先置空再删"，直接 DELETE 会报外键违规，清理任务停在 failed。
- 建议：明确先 UPDATE 置空再 DELETE；或对这两个纯技术指针使用 PostgreSQL 15 起支持的列子集语法 `ON DELETE SET NULL (avatar_asset_id)`。多列外键不能写普通 SET NULL，那会把 account_id 一起置空。采纳 M8 后 assets ↔ asset_uploads 这一条消失。

### M12. 文档之间的矛盾与未定义项

- 错误码表（接口设计 1.4）缺少正文用到的 SNAPSHOT_NOT_READY（4.3）、RESTORE_UNAVAILABLE（§5）、ACCOUNT_ALREADY_EXISTS（3.1）、上传确认窗口超时、改币种时需先清空预算与预计费用的错误码（总览 §3）。建议以 1.4 为唯一清单，标注 HTTP 状态，放入 packages/contracts。
- 预订字段矩阵（接口设计 3.6）写"住宿、预约与其他类型使用 provider_name、address、start_local、end_local、contact_*"，按字面 transport 不能存承运方与出发到达时间；数据库 §12 的说明却是"承运方、酒店或预约方"、"出发、入住或预约开始"。建议给出 kind × 允许字段矩阵，两份文档引用同一张表。
- "重新鉴权"（接口设计 2.7、总览 5.2）与 REAUTH_REQUIRED 的"5 分钟内验证密码"混用。若下载图片要输密码则不可用。建议统一：下载授权只需有效访问令牌加归属校验，"近期认证"专指 REAUTH_REQUIRED。
- JournalEntryCreate 的 recorded_on 默认 null（旅行级），PhotoCreate 默认旅行时区今天（接口设计 3.6）。TR-08 强调途中随手记录，笔记默认变成旅行级不合理。见 Q7。
- LedgerEntry 响应含 currency_code 但 ledger_entries 无此列，行程 estimated_amount 要求携带 currency_code 却"不回显"。建议两处统一从 trip 派生并回显，数据库文档注明派生规则与快照来源。
- 未定义：同步变更字段 version/kind/data 与 sync_changes 列的映射；Asset.sha256 的 JSON 编码（hex 或 base64）；TripOverview.finance_summary 的字段；ItineraryItem.kind 与 Asset.status 的对外枚举（pending_delete 是否对外）；DataSnapshot=failed 时 items 接口的行为；ExportJob 不回显 filters。
- 状态码不统一：TRIP_DELETED 对 GET 也返回 409；ASSET_NOT_READY 用 422 而 SNAPSHOT_NOT_READY 用 409；OFFLINE_OPERATION_NOT_ALLOWED 用 403。建议读已删除旅行返回 410，"未就绪"统一 409，不允许的离线操作类型用 422。

### M13. 有关联退款的支出删除语义与其他删除不一致

- 位置：接口设计 2.5、3.5；数据库 §10 规则 REFUNDS_EXIST。
- 问题：删除行程、预订、笔记都是自动解除关联并保留记录，唯独删除带退款的支出要求先逐条改退款；删除一笔带 2 笔退款的支出需要 3 次写。
- 建议：删除支出时同事务将关联退款的 refunded_entry_id 置空（变为独立退款），返回警告 REFUNDS_UNLINKED。

### M14. 同步批中的瞬时失败没有可重试语义

- 位置：接口设计 4.1 SyncPushResult 的 status 只有 applied、replayed、conflict、rejected、dependency_failed。
- 问题：数据库超时或依赖不可用落到哪一类未定义，客户端无法区分"可重试"与"已拒绝"。
- 建议：逐操作结果增加 retryable 标记，或瞬时故障时顶层返回 503 并保证此前成功的操作已有收据。

### M15. request_hash 的规范化规则未定义

- 位置：接口设计 1.2"REST 与 sync/push 的同一业务命令使用一致的规范化指纹"；数据库 §20。
- 问题："128.50" 与 "128.5"、null 与缺省字段、键序、Unicode 归一化都会让同一操作的重试被判为 IDEMPOTENCY_CONFLICT。
- 建议：对内部命令结构体做确定性编码后哈希并写明规则；或 P0 只比较 (operation_type, entity_id)，相同 operation_id 一律视为重放。

## 2. 建议简化（不损失 P0 需求）

### S1. 取消快照表与快照任务，改为"记游标、读活表、追平"

- 位置：总览 4.3；接口设计 2.8、4.3；数据库 §22–§24。
- 现状：baseline 与 trip_reload 都是异步任务：创建快照 → 轮询 → 分页下载 → 核对，涉及 3 张表、一个 worker 任务、3 个接口、SNAPSHOT_* 错误码、24 小时过期与失效状态；每次 baseline 把所选旅行全部数据复制进 snapshot_items。新注册的空账号在安卓首次同步也要走这套流程。
- 替代方案：客户端先取当前 last_seq 作为起始游标 C（可由 /sync/status 返回签名游标），再通过 `GET /sync/bootstrap?trip_id=&cursor=` 按 (entity_type, id) 分页读取活表当前态（不需要一致切片，limit 可到 500），读完后从 C 开始消费变更日志，期间的修改按版本比较覆盖。任何在 C 之后发生的变更都会通过日志回放，读到的行无论新旧都能被正确覆盖。CURSOR_EXPIRED 也走同一流程。
- 导出：worker 内用一个 REPEATABLE READ 只读事务分页流式写 ZIP；个人数据量下秒级完成；文件按 asset_id 在事务外下载，缺件即失败重试（现有规则）。export_jobs.snapshot_id 删除。
- 收益：删除 data_snapshots、snapshot_items、snapshot_asset_refs 三表与相关 worker、接口、错误码；M4 随之消失；客户端不再有快照状态机。

### S2. 全部旅行的结构化数据都同步到本地，"选择离线旅行"只控制文件下载

- 位置：总览 4.3"客户端保留全部旅行的基础信息，只保留已选择旅行的详细数据"；需求 AC-02。
- 分析：个人账号的全部结构化数据是 KB 到 MB 级（重度用户 50 趟旅行按上限估算也在几十 MB 内）。按旅行选择详情导致：trip_reload 流程、requires_snapshot 标记、"新选旅行补齐再继续增量"、"其他详细变更扫描后丢弃"，以及移动端同一页面要同时维护本地库与 REST 两条数据路径。
- 建议：所有结构化数据本地化，用户选择的只是"下载该旅行的照片与附件"；回收站旅行本地保留并隐藏，恢复不需重新下载。这是对 AC-02 表述的调整，需要产品确认（Q6）。

### S3. 服务端保证页面不切开批次

- 位置：总览 4.2"页面可能切开同一变更批次"；接口设计 4.2。
- 建议：拉取时读到 batch_end_seq 再截断，允许为完成批次略超 limit（批次大小受单事务影响行数限制，可为重排与模板应用设上限）。客户端每页一个本地事务、一个进度，不再需要暂存区与"扫描进度、应用进度"双记录。

### S4. 去掉 redacted 变更类型，允许序列空洞

- 位置：总览 4.4；数据库 §19 change_kind。
- 分析：每个批次只涉及一趟旅行（所有操作带 trip_id，创建旅行的两条日志也同旅行）。永久删除时按 (account_id, trip_id) 直接删除整批日志行不会切开批次。游标语义是"已消费的最后 seq"，只要求单调不要求连续。
- 建议：删除 redacted 及其 CHECK 分支；客户端规则改为"收到 trip purge 事件时丢弃该旅行未收齐的暂存批次"；加集成测试断言"同批次 trip_id 唯一"。

### S5. 去掉 entity_tombstones，旅行永久删除保留存根行

- 位置：总览 4.4；数据库 §21。
- 分析：每种资源创建时多查一张表，purge 要为每个 ID 写墓碑。所有子实体都归属旅行，只要 trips 行以 purged 状态保留（新增 purged_at，清空可清空字段，放宽 name 的长度 CHECK），任何引用该 trip_id 的创建或更新都会被拒绝，子表 ID 复用由存根加子行主键天然阻止。创建重放本身已由 mutation_receipts 拦截；不同 operation_id 复用同一 UUID 属于客户端缺陷。
- 建议：删除该表；单条软删记录不单独物理清理，随旅行永久删除一起清；头像资产的墓碑随 avatar 引用规则处理。

### S6. mutation_receipts 设置 TTL

- 位置：数据库 §20"没有固定 TTL，账号注销时删除"。
- 分析：创建重放会撞 entity_id 主键或旅行存根而不是产生第二笔；更新重放会被版本校验拦下。永久保留只增加一张每写一行的增长表。
- 建议：TTL 取大于日志保留期的值（如 180 天）并补 created_at 索引；过期后的创建重试返回 ID_ALREADY_USED，客户端视为已成功并读取当前版本。

### S7. 去掉 depends_on 与 commit_cursor

- 位置：接口设计 4.1、1.4。
- 分析：服务端按批内顺序处理，同一 entity_id 的前序操作失败即可自动返回 dependency_failed，不需要客户端声明依赖及环检测。commit_cursor 文档自己规定"不得用于跳过变更"，没有实际用途；若要实现 read-your-writes，让客户端在写后立即拉取即可。SyncPush.client_id 若仅用于日志需注明。

### S8. 账号注销的只读凭证机制过重

- 位置：接口设计 2.9、§5；数据��� §26 receipt_token_hash。
- 分析：receipt_token、renewDeletionReceipt、自定义 `Authorization: Deletion` 方案、7 天保留，目的只是"注销后能查进度"。
- 建议：deleting 状态下允许现有会话只读查询任务；完成后邮件通知。删除 2 个接口、1 个认证方案、2 列。

### S9. trip_budgets 并入 trips

- 位置：数据库 §8；接口设计 2.5。
- 分析：预算与旅行 1:1，独立版本、独立 ETag、独立同步实体类型，创建旅行要写两条变更快照。
- 建议：total_amount 作为 trips 列，category_budgets 随 trip 版本变化；`PUT /trips/{id}/budget` 保留为便捷接口但递增 trip 版本。

### S10. 可选的进一步简化

- JWT 每请求都查会话，无状态性为零：access token 可改为不透明随机值（哈希与会话同表），省去 jwt 库、签名密钥与轮换、iss/aud、时钟偏差，撤销即时生效。若保留 JWT，需补签名密钥 kid 与轮换。
- CSRF 三重防护可减为一重：`__Host-` Cookie + SameSite=Lax + Origin/Sec-Fetch-Site 校验已足以阻断跨站 POST，双提交 token 与 csrf_token_hash 列可去掉。保留也无害，但多一条客户端必须实现正确的规则。
- purgeTrip 不必要求 5 分钟内密码复验：AC-03 只要求"明确确认范围和不可恢复的结果"，confirm=true + If-Match + 幂等键即可；密码复验保留给账号注销。
- 后端结构 §5 的"每个用例在 ports.go 声明窄接口"可改为每模块一个仓储接口；workflows 只保留四处（三类删除解关联、概览聚合、同步分发、导出与清理）。
- 跨日移动只能走重排：允许 `PATCH scheduled_on`（追加到目标日末尾），重排接口只校验集合（ORDER_CHANGED）。

### S11. 同一实体四份表示需要合并为一份来源

- 位置：后端结构 §5、§9"HTTP generated 只被 HTTP 层使用"；总览 4.1"白名单快照"。
- 问题：OpenAPI 生成模型、业务模型、sqlc 行、同步/快照/导出白名单 JSON 四种表示，11 类实体乘以四向转换约 50 个映射函数；写变更日志的适配层不能复用 API 序列化，只能再手写一份白名单。接口设计 4.2 示例里同步 data 与 LedgerEntry 资源已经完全相同。
- 建议：规定"同步与导出 payload = API 资源 schema"；把生成的模型（非 server stub）放到可被 modules 与 adapters 导入的中性包，或用 oapi-codegen 的 `x-go-type` 让资源 schema 直接指向业务模型。同时补两项实现前提：PATCH 的"缺省 vs 显式 null"需要 nullable 类型支持；NUMERIC 需要 sqlc 类型覆写到十进制类型。

| Q4 | "跳过"行程是否解除关联 | 需求 TR-01 关键规则与数据库 §5 都规定 skipped 立即解除待办、账目、预订、资料、笔记的关联，且恢复 pending 不还原；功能清单 §7.3 的例子恰是"跳过景点时不可退门票支出继续保留"，保留了记录却丢了它属于哪个景点，误点一次即永久丢失 | 只有删除解除关联，跳过不解除；需要同步修改需求文档 |
| Q5 | 币种锁定能否解锁 | trips.currency_locked_at"首次创建账目时设置，以后不清空"，记错一笔并删除后永远不能改币种 | 允许"无有效账目"时解锁，或界面明确提示"首笔记账后不可更改" |
| Q6 | 是否采纳 S2 | 全部结构化数据本地化会改变 AC-02"选择需要离线使用的旅行"的含义 | 建议采纳，"选择"只针对文件下载 |
| Q7 | 笔记 recorded_on 默认值 | JournalEntry 默认 null（旅行级），Photo 默认当天 | 建议笔记默认当天，旅行级用显式 null |
