### 1.1 兼容与启用

- 新入口使用 `/api/v1/sync/*`；`GET /sync/status` 返回明确的 `supported_protocol_versions=[2]`、`recommended_protocol_version=2`、`sync_epoch`、`server_time`、限额与保留期限。其他同步请求必须提供 `X-Tripfolio-Sync-Version: 2`；缺少或不支持返回 426 `SYNC_PROTOCOL_UNSUPPORTED`，在任何写入前拒绝，不默认为旧 LWW 规则。

- 首次启用 v2 必须先完成账号基线；不能拿普通列表分页代替一致快照。旧原型队列须迁移并保留原始内容，不能把旧 split_count 直接发作现行分摊输入。旧文档无基线的状态操作不接受为 v2 操作。

## 2. 标识、值与本地/远端边界

- 账号身份只取已认证会话；`client_id` 是本安装标识，不是权限凭证。任何 entity/trip/asset/依赖引用均须校验账号和旅行归属。不能通过正文账号 ID、另一账号的收据、Share 令牌越权。
- 实体和操作使用稳定 UUID，允许 v4/v7；从本地创建起保留同一 ID，绝不上传后换 ID。已删除/永久删除实体的 ID 不复用。离线新建旅行额外携带 `self_member_id`，在同一事务创建该 ID 的「我」成员，使后续付款/分摊可稳定引用；旧 REST 创建旅行仍保留原有默认流程。
- version、seq、batch_end_seq 采用无前导零十进制字符串，version≥1、seq≥0，数值上限为有符号 int64；不得转浮点数做比较或运算。客户端用精确十进制整数操作或平台精确整数能力。金额为规范十进制字符串，沿用币种精度和退款正数规则，不使用二进制浮点计算分摊。
- 日历日期为 `YYYY-MM-DD`，当地时间不附偏移，按旅行 IANA 时区解释；系统时间为 UTC RFC3339。离线命令入队前冻结实际日期、币种、时区及分摊参与人，重连不把“今天”改成上传日，也不重新套用届时默认成员。服务端仍重新校验其有效性。
- PATCH 缺失字段表示不修改，显式 null 只用于可清空字段；未知字段、错误枚举和派生只读字段拒绝。白名单资源不包含对象存储键、签名 URL、凭证或本机文件路径。
- 服务端 version 仅属于已确认状态。本地编辑使用独立 `local_revision` 和操作序列；不冒充远端 version 递增。读视图等于“已确认基线 + 按依赖顺序的未同步覆盖”，本地修改、覆盖层和队列要么一同持久化，要么全部失败。
- 无有效地点的行程先保存设备草稿，状态 `needs_place`，不向服务器伪造坐标/搜索结果；补齐用户确认的地点和所有业务必填项后才产生可推送命令。依赖此草稿的操作保留本地等待。地图、路线与在线模型能力不能仅因旅行离线就绪而被称为可离线运行。

## 4. 版本、集合与关联冲突

### 4.1 实体基线与关联字段组

普通 update 允许使用旧 base：只有完整版本历史可证明本次写字段及其关联组与后续变更不相交，才合并并返回 MERGED_WITH_NEWER_VERSION。相交、历史不全、base 比当前新、目标已删除均不静默覆盖。delete、restore、archive、状态赋值必须精确版本相等，禁止借“目标值相同”绕过并发校验。成功收据重放先于这些业务校验，但仍须通过账号/会话授权。

| 业务范围 | 冲突比较时必须合并处理的字段/关联 |
| --- | --- |
| 旅行 | start_date/end_date/timezone；currency_code/budget_amount/currency_locked_at 及存在的账目/行程预计费用；改币种仍遵守锁定/清空金额规则 |
| 行程 | scheduled_on/sort_order 与相关日期集合；预计费用/币种；计划/实际起止时间各自成组；地点名/地址/经纬度成组 |
| 账目 | amount/currency_code/payer_member_id/split_mode/participant_member_ids/splits/personal_amount/split_count 成一财务组；kind/refunded_entry_id 与退款总额校验关联；category_id 与有效分类引用校验；票据关联集合整体校验 |
| 成员 | 整个旅行有效成员集合，包括名称、比例、顺序、is_self、增删及版本；账目财务修改基于对应集合 guard |
| 预订/资料 | reservation.kind 与受该类型约束字段；时间起止成组；document.reservation_id/asset_id 与引用归属和删除状态 |
| 清单/待办 | 清单 name/category 共同决定唯一性；status 单独精确版本赋值；todo.completed 与 completed_at 成组，due_on 的日期解释按旅行时区 |

### 4.2 集合 guard

guard 是乐观并发前置条件，不是授权令牌。kind 封闭为 categories、members、itinerary_day、packing_order、todo_order、photo_day；scope_id 分别为账号 UUID、旅行 UUID、`tripUUID/YYYY-MM-DD`、旅行 UUID、旅行 UUID、`tripUUID/YYYY-MM-DD`。服务器从认证上下文核验这些范围。

revision 为 `sha256:` 加小写十六进制摘要。摘要 UTF-8 原文是 `sync_epoch + LF + kind + LF + scope_id + LF`，后接该范围全部有效、已确认资源按小写 UUID 字节升序排列的 `id:version + LF`；不存在条目时保留前缀，软删除不在有效集合。排序/日期/任何成员字段更改必须递增资源版本，因此摘要可检测新增、删减、重排与修改。完整快照和稳定集合读取可返回 revision；客户端只能从完整的已确认镜像计算，不能从待同步覆盖或不完整页面计算。guard 不能解析为同步游标。

集合命令在同一账号事务锁内对比 revision；不同则 412 COLLECTION_CONFLICT，不按旧集合覆盖新成员，不拆开百分比/顺序原子操作。涉及多日期必须同时核对所有相关 guard；任意不符整项不写入。操作结果持久保存受影响集合的新 revision，使后续操作可以引用精确提交后的集合状态。

旧 Web 的成员 PUT 没有 base，财务编辑也未携带成员集合 guard。采用确定的两阶段发布：先给现行 REST 兼容添加 guard 并升级当前 Web，使成员整体保存和会重算分摊的财务写入都携带 guard；尚未启用 v2 的账号继续旧行为。账号启用 v2 后，所有这些写入口（不只标记新版的请求）必须校验 guard，缺失返回 428 COLLECTION_BASE_REQUIRED，旧 Web 提示刷新升级并保留输入，绝不回退无基线写入。其他在线接口和读取保持兼容。服务端每次成员变化仍递增版本并写日志，让鸿蒙发现旧/新 Web 修改。H07/H12 未完成 Web 升级、全入口强制和回退提示验证前不得开放该账号 v2，不能把兼容模式算作双端无静默覆盖验收通过。

## 5. 不可变操作、依赖与重复执行

SyncOperation 固定字段：operation_id、type、entity_type、entity_id、trip_id、base、guards、depends_on、payload。operation_id 永久唯一；entity_id 对表中集合操作允许 null，其他为稳定实体 ID；账号级分类 trip_id=null，其他为目标旅行 ID。guards/depends_on 必填数组。账号 ID、客户端时间和 source 不参与权限判定。

base 只能为：创建/集合操作的 null；已确认实体的 `{version}`；或 `{operation_id}`，引用另一成功操作对本实体记录的提交版本。guard 项只能为 `{kind,scope_id,revision}` 或 `{kind,scope_id,operation_id}`，后者引用该成功操作持久保存的提交后集合 revision。引用操作必须在 depends_on 中。禁止引用响应中可能已刷新的 data.version 推断原提交版本，禁止假设“本地创建后每改一次远端一定加一”。

- depends_on 最多 100 个不同 ID；同批只允许引用更早的操作，跨批只允许引用本账号已成功收据。前向、自依赖、环、不同账号引用均拒绝；未提交依赖返回 dependency_failed，不偷查其他账号是否存在。实体创建、旅行创建、分类/成员/资产引用和本实体连续编辑必须建立需要的依赖链。
- 提交序列按拓扑顺序处理；一个操作一个事务（其中的业务关联写原子），不整批长时间锁账号。失败只影响其依赖后继；独立旅行和独立操作继续。同一实体的后续操作在前项未成功/冲突未解决时不越过提交。
- 本地已入队内容不可变；重试原样发送相同 ID、base/guard 引用、payload。用户修改已排队内容产生新操作；从未发送且无被引用后继时可本地撤销整条命令并重放覆盖层，不能改写旧 ID 正文。发送状态不明时禁止以新 ID“重试”，先查/重放原 ID 得到明确结果。
- 请求指纹以服务端规范化命令计算，包含协议版本、type、目标、原始 base/guard 引用、依赖及 payload；金额/UUID/默认值按同一白名单规范化，集合仅在语义无序时排序，用户可见顺序保留。同账号同 ID 不同指纹返回 IDEMPOTENCY_CONFLICT；同步入口与其业务事务的收据写入同事务，不能在业务提交之后另存同步收据。
- 成功收据保存不可变 result.references（每个实体本次实际提交版本）、scope_revisions、commit_seq、指纹和 applied 状态；重放只重新读取当前可见 data，可能为 null，不更改上述原提交事实。允许复用统一 Writer 并扩展收据字段，不复制业务规则。
- 去重证明保留至账号永久注销：禁止按 90 天日志保留期删除成功 ID/指纹和原提交版本/集合引用。大响应正文不入收据；永久删除脱敏后仅保留不可逆指纹、ID和必要版本事实。清理若无法保留某旧结果，必须拒绝自动重执行并要求人工核对，不能把“找不到收据”默认为从未成功。
- 冲突解决先拉取/核对最新基线，生成新 ID 的替代操作；原操作持久标记 superseded，相关后继以新 ID 重建且保留替换关系。不能静默修改旧操作、复活已删除实体或丢弃原草稿。恢复旧数据使用允许的 restore 或用户确认的新建复制，永久删除不得 restore。

## 6. 同步接口、结果与重试

本节路径均以 `/api/v1` 为前缀；身份使用原生 Bearer 会话，拒绝 Share 身份。新同步错误沿用 problem+json 的 code/detail/conflict 结构。

| 方法/路径 | 请求 | 响应及约束 |
| --- | --- | --- |
| GET /sync/status | 认证；不要求已有游标 | supported_protocol_versions、recommended_protocol_version、sync_epoch、server_time、retention_days=90、snapshot_ttl_seconds=86400、limits；无可推进进度的游标 |
| POST /sync/push | `{sync_epoch,client_id,operations}`，协议头必填；操作结构见第 5 节 | `{sync_epoch,results}`，结果与请求 operation_id 一一对应并保持顺序；合法批次 HTTP 200，逐操作返回结果 |
| GET /sync/changes | cursor 必填，limit 默认 200、最大 500 | `{sync_epoch,changes,next_cursor,has_more}`；返回完整事件记录，分页规则见第 7 节 |
| POST /sync/snapshots | Idempotency-Key；`{sync_epoch,purpose,selected_trip_ids}`，purpose=baseline/trip_reload | 202 `{data:DataSnapshot}`；同键同正文找回同一任务，失效/失败后另用新键创建；只接受本人范围 |
| GET /sync/snapshots/{id} | 认证、协议头 | DataSnapshot；状态 queued/building/ready/failed/invalidated/expired；错误不虚报 ready |
| GET /sync/snapshots/{id}/items | cursor 可空，limit 默认 200、最大 500 | `{snapshot_id,sync_epoch,items,next_cursor,has_more,item_count,high_water_seq,baseline_cursor}`；末页才提供 baseline_cursor；trip_reload 的此字段始终 null |

limits 明确 max_operations=100、max_operation_bytes=65536、max_request_bytes=1048576、max_dependencies=100。请求大小按 UTF-8 解码前后的受限读取处理，不能解压后绕过上限。结构、未知类型、重复 operation_id、非法依赖图、协议/epoch 或顶层身份错误在执行任何操作前拒绝；字段级业务校验、版本/引用失败进入对应逐操作结果。不把 100 项调用包装成一个长期账号锁事务。

每条成功结果为 `{operation_id,status,result}`，status=applied/replayed；result 包括 references、scope_revisions、commit_cursor、warnings、data。references 与 scope_revisions 是原提交事实，data 是当前可见资源或 null；commit_cursor 仅是提交标识，不接受为拉取 cursor。成功无业务变化可 references 为空、commit_cursor=null，但仍保存成功收据。

每条失败为 `{operation_id,status,error}`，error 包括 code、http_status、retryable、detail 和可选 conflict。conflict 只含本账号可见的当前资源、expected/current version、conflicting_fields 或集合 kind/scope/revision；列表过大时返回需重新读取的范围，不泄露其他账号引用对象。

| status / 错误 | HTTP 语义 | 客户端动作 |
| --- | --- | --- |
| conflict：VERSION_CONFLICT / COLLECTION_CONFLICT / MERGE_HISTORY_UNAVAILABLE | 412，retryable=false | 持久冲突草稿与原基线，拉取最新内容后由用户解决 |
| rejected：OFFLINE_OPERATION_NOT_ALLOWED / VALIDATION_FAILED / INVALID_REFERENCE | 422，retryable=false | 保留覆盖与错误，用户修正生成新操作；不得清空队列 |
| rejected：IDEMPOTENCY_CONFLICT | 409，retryable=false | 停止该操作，核对原 ID 和内容；不得自动换 ID 重试 |
| rejected：RESOURCE_GONE / TRIP_DELETED / RESTORE_UNAVAILABLE | 410 或现有业务状态码，retryable=false | 保留本地草稿，按允许范围恢复/复制；不自动复活 |
| dependency_failed：DEPENDENCY_NOT_APPLIED | 424，retryable=true | 等依赖明确成功再原样重试；后继不执行 |
| dependency_failed：DEPENDENCY_REJECTED | 424，retryable=false | 祖先已冲突/拒绝或被替代，提示一起处理依赖链 |
| failed：DEPENDENCY_UNAVAILABLE / INTERNAL_ERROR | 503/500，retryable=true | 原操作保留、退避重试；不能由客户端判断未曾提交 |
| 顶层 SESSION_EXPIRED / ACCOUNT_BANNED / ACCOUNT_DELETING | 401/403，按账号服务现行规则 | 暂停该账号推送，恢复身份后重试；既已提交的独立操作不回滚 |
| 顶层 SYNC_PROTOCOL_UNSUPPORTED / SYNC_EPOCH_MISMATCH | 426/409 | 停止该轮写入；升级或进入 epoch 恢复流程，保留所有本地内容 |
| 顶层 INVALID_CURSOR / CURSOR_EXPIRED | 400/410 | 不改本地确认进度；前者校核账号/游标，后者重建基线 |
| 顶层 RATE_LIMITED / 请求超限 | 429/413 | 遵循 Retry-After；超限批次按操作边界拆分，单一原子操作超限不能拆为半完成 |

身份在批次中途失效时停止剩余操作；返回顶层身份错误可能无法携带已成功结果，客户端将整批标记“结果待确认”，恢复登录后原样重试全部操作，由收据找回已成功项。连接中断/超时也按此处理；不得用 HTTP 失败推断数据库必未提交。

同一账号只运行一个客户端同步调度器。启动、前台、联网恢复、手动刷新合并触发；先拉取可用变更并维护覆盖层，再按可执行依赖推送，随后拉取确认。失败采用 2 秒起、指数增加、上限 5 分钟的带随机抖动退避，遵守更长 Retry-After；网络离线时不忙轮询。手动刷新可提前一次网络尝试，但不跳过冲突、身份或限流约束。缓存满/磁盘失败必须暂停并报告未保存，不能先更新 UI 成功状态。

## 7. 增量、批次、删除与保留边界

SyncChange 字段：seq、batch_id、batch_end_seq、entity_type、entity_id、trip_id、version、kind、schema_version、requires_snapshot、changed_fields、data。实体枚举沿用 trip、trip_member、expense_category、itinerary_item、ledger_entry、packing_item、todo、reservation、document、photo、asset；新排序字段属于原资源，不另造无版本旁路。schema_version 本协议初始为 2；version/seq 为精确字符串。upsert 的 data 为该版本白名单对象、changed_fields 为实际改动；delete/purge/redacted 的 data 和 changed_fields 为 null。

1. 游标由服务器签名并绑定账号、sync_epoch、协议、用途、扫描位置及当前轮次上界。首次从 baseline_cursor 开始；每轮固定上界 H。中间页 next_cursor 继续同一 H；终页 next_cursor 是 after_seq=H 的 checkpoint，下一次才捕获新的 H。不得以设备时间、列表游标、commit_cursor 或 status 响应生成进度。
2. 不按旅行过滤全局增量。所有旅行基础、分类必须维护；未选择详情的旅行可跳过详情正文应用，但仍记录已扫描范围、删除标记及“详情未下载”。新增选择只能通过 trip_reload 获得完整资料，不能凭曾扫描到几条事件标为离线就绪。
3. seq 单调有序；页可以截断业务批次，客户端先事务持久化整页至 inbox 并保存 scan_cursor，再请求下一页。只有 batch_end_seq 已完整收齐、schema 可理解且关联校验通过，才原子应用整个批次并登记 batch_id 与 apply_cursor。apply_cursor 只越过连续已处理批次；未知实体/schema、缺页/缺依赖不得推进应用确认。
4. 独立后续批次可被记录为已处理并应用到其他旅行，但保留全局连续应用断点；不得因一个冲突/补充下载阻塞其他旅行推送。重启用持久批次标记跳过已应用版本，inbox 空间不足时停止继续拉页而不是丢缓冲。
5. 远端 upsert 先更新确认层，再重放仍有效的本地覆盖；相交变更生成持久冲突，不直接覆盖用户视图。重复版本事件幂等；低于已确认版本的 upsert 不能回退。delete 标记逻辑删除，trip.delete 作用于整个旅行的确认层；purge 永久移除可见确认数据并保留必要删除事实，本地未同步草稿移入隔离冲突区，不因删除而丢失。
6. redacted 仅说明旧正文已被服务器清除，只推进扫描，不复活/覆盖实体。真正删除动作由对应 delete/purge 执行。服务器永久清理需先失效相关快照、清除历史正文并发出墓碑/标记，保持现有清理顺序；账号注销后所有身份和本地原账号访问策略见第 9 节。
7. requires_snapshot=true 表示对应范围不能仅凭该事件恢复完整详情：持久记录范围和触发 seq，立即撤销其“离线就绪”；取得高水位不低于触发 seq 的 trip_reload 并核对后才视为该批次完成。可继续扫描/处理独立范围，不能用 reload 的 H 跳过全局事件。触发范围已被删除则按删除终止 reload 并保留草稿。
8. 日志默认保留至少 90 天；retained_after_seq 是已不可再完整读取的边界。after_seq 小于该边界返回 CURSOR_EXPIRED，即使某些未清日志尚在；完整历史不足时 PATCH 返回 MERGE_HISTORY_UNAVAILABLE。日志清理和字段合并使用同一边界，不能误以为空字段集代表安全合并。活动快照在有效期内必须钉住其 H 之后的日志，或先失效快照再推进边界。

### 7.1 数据库恢复与 sync_epoch

sync_epoch 是服务器数据连续性的 UUID。账号首次建立同步域时生成；从备份恢复、重建或丢失收据/日志连续性时必须在重新开放写入前轮换，不能沿用恢复文件中的旧 epoch。所有同步游标、快照与 push 都绑定它。相同 epoch 内承诺成功收据不会遗忘；跨 epoch 不作此承诺。

epoch 不匹配的 push 在任何写入前返回 SYNC_EPOCH_MISMATCH；客户端保留旧确认层、操作和文件，取得新 baseline 后将旧队列及此前“已成功但新基线缺失”的本地记录作为待核对项。不能自动给旧操作换 epoch 或新 ID 重发，因为数据库恢复可能撤销了原提交。用户确认恢复哪些内容后才生成新 epoch 的新操作。H07 必须接入已有数据库恢复流程并验证该停写/轮换点；未完成前不能声称恢复后同步一致性成立。

## 8. 基线、详情下载与重新对齐

DataSnapshot 包括 id、purpose、selected_trip_ids、status、schema_version、sync_epoch、high_water_seq、item_count、captured_at、expires_at、error_code。high_water_seq 和 captured_at 在 ready 前为 null；item_count 只在 ready 时为最终数量。有效期默认自捕获时起 24 小时；必须明确 UTC 绝对过期时间。任务失败、取消权限或失效不能返回部分数据冒充 ready。

- baseline 包含本账号全部有效分类、所有旅行基础及回收站旅行基础、所选有效旅行完整详情和资产元数据；不含文件字节、账号凭证、分享令牌、签名 URL。trip_reload 只包含所选有效旅行的完整详情、该旅行基础及其依赖的账号级分类，不改变全局同步基线。category 版本只向前合并，不用部分分类集合替代账号完整分类镜像。
- selected_trip_ids 去重；baseline 可为空，trip_reload 至少一趟。属于本人但已永久删除的旅行根据墓碑剔除，回收站旅行只提供基础；跨账号/从未属于本人 ID 返回统一 404。响应给出实际选中范围，客户端核对剔除内容并保留该范围的未同步修改。trip_reload 对已无效目标返回删除/失效结果，不建空壳旅行。
- 捕获 H 和所有业务行必须来自同一个数据库 MVCC 视图。快照 worker 可使用独立 REPEATABLE READ 事务物化不可变条目，但不在此事务等待账号写锁；普通写仍保持 accounts→account_sync_state 锁顺序。快照发布 ready 前在账号锁内重新核对任务、epoch、账号状态及失效代次；并发永久清理可使任务 invalidated，不能把清理前读取的正文重新发布。
- 快照创建先登记任务与失效代次，清理流程必须覆盖 building/ready 快照及资产引用。分块生成不能每批读取新的业务视图；大数据无法维持一致视图时任务失败，重新创建，不能用分块的不同 H 拼出快照。每次 items 读取重新校验身份、过期和失效状态。
- items 按固定 ordinal 连续分页，一项包含 ordinal/entity_type/entity_id/trip_id/version/data；同一快照同一项不可变化。分页游标绑定快照 ID、账号、epoch、H 与 ordinal，不能拿另一快照或普通列表游标续页。最后一页给出最终 item_count 和 baseline_cursor（仅 baseline）；校核 ordinal 连续、实体唯一、数量、schema、引用关系以及所选范围完整性后才允许采用。
- 客户端下载到 staging 区；中断后根据 snapshot ID 和页断点恢复，不能先清空当前数据。快照已过期/失效时丢弃或隔离这份 staging，原确认层/草稿/队列/文件继续保留，然后重新创建。
- 完整安装 baseline 时，在一个本地事务切换新确认层、保存 H/checkpoint、处理该范围旧确认层中缺失实体并重新挂接覆盖。保留版本高于快照或 seq 高于 H 的已确认更新和删除事实；范围外数据不按“快照缺失”删除。pending/conflict/failed 草稿、依赖引用、未上传文件和 AI 确认记录不由快照覆盖。使用 staging 表/代次切换控制原子性，不能逐表覆盖暴露混合代次。
- trip_reload 只更新目标旅行，不能推进全局 scan/apply 游标。保留该范围已应用的 H 之后事件并重放；有界缓冲不足则重建 reload，不跳过事件。完成后还要从全局 checkpoint 继续拉到当前，只有“资料完整、无待补范围、所选文件校验完成”的部分才标记离线就绪；同步冲突/待上传与就绪程度分别展示。
- 一般 CURSOR_EXPIRED 不改 epoch：重新 baseline 后可继续用原 ID 原样提交尚未确认操作，收据仍可去重；与第 7.1 节数据库恢复导致的 epoch 改变严格区分。基线之前的原始编辑依据仍保留，服务端历史不足时让用户处理冲突，不把新快照版本偷偷填回旧操作。

## 9. 本地业务层、账号与缓存

H06 提供本地事务与账号隔离；各业务模块提供 read/validate/preview/commit 服务；H08 独占同步队列、收据、inbox、游标和确认层更新。页面与 AI 只调用这些服务，不能自行写数据库或直接向远端写接口绕过队列。允许共享少量明确类型，不建立能任意调用所有表的通用“AI SQL”接口。

本地持久记录至少包含：owner_account_id、sync_epoch、local_schema_version、server_state、local_overlays、immutable_operations、operation_dependencies、operation_receipts、conflicts、inbox_batches、snapshot_staging、download_scopes、file_tasks。可以是表或等价事务结构，但原始编辑基线/前镜像、local_revision、错误/重试时间、来源及依赖引用必须能重启恢复；不能只存最后一份 UI 表单或 queued 布尔值。

| 本地接口职责 | 必须持久化/校验的内容 |
| --- | --- |
| read | 从确认层与覆盖生成视图，返回 local_revision、远端 version、同步/冲突状态、资料完整范围及最后确认时间 |
| preview | 校验当前账号、业务引用、完整范围和权限边界，计算影响实体与本地前镜像，记录预览依赖的 local_revision；不产生远端写入 |
| commit | 同一数据库事务校验预览依赖仍成立，保存覆盖、不可变操作/依赖及稳定 operation_id，递增 local_revision；成功后才能向用户显示“已保存到本机” |
| reconcile | 消费完整远端批次、更新确认层，按依赖重放覆盖并产生冲突；原始未同步正文不因版本变化丢弃 |
| resolve / undo | 基于当前版本生成替代/补偿操作，保留原操作与前镜像关联；已成功操作的撤销仍可能冲突，不声称服务器事务回滚 |
| maintain | 清理已无引用的确认缓存/完成任务产物；不能删除未同步覆盖、冲突、结果未明操作、上传原文件或未安装的完整恢复证据 |

操作传输状态使用 queued、sending、uncertain、retry_wait、waiting_dependency、applied、conflict、rejected、superseded、cancelled；传输状态可变，操作内容不可变。sending 在进程重启后归为 uncertain 并按同 ID 重放；applied 需要成功收据，不能由网络在线、队列为空或读取资源存在推断。conflict/rejected 不阻塞独立旅行；本地视图明确“待同步/冲突/失败”，不能把失败草稿计入已确认统计而不说明。

首次登录须联网；已有账号可在离线状态使用此前解锁的本地资料和保存操作，过期 access token 本身不删除资料。恢复网络后必须先验证账号状态，未授权时暂停推送；离线期间无法保证及时感知服务器封禁，界面不宣称仍有远端权限。显式退出/切号前展示待同步、冲突和待上传数量；用户确认退出后关闭当前数据库/文件访问，清除会话凭据，保留原账号私有资料，只有原账号再次认证后才能恢复访问。不能把保留队列迁到新账号，不能因同邮箱显示名相同认定同账号。

各账号数据库、文件目录和本地密钥按稳定账号 ID 隔离；schema 迁移先检查结构版本与未同步载荷，事务迁移或保留可恢复副本，失败拒绝打开新结构；高于当前程序的 schema 不降级覆盖。旧本地 v2 账目载荷映射为需要用户核对分摊的草稿，缺失付款人/参与人不能按当前所有成员静默填充后推送。清缓存只删除可重新获得的已确认副本，并先降级对应离线范围；用户要求彻底清除未同步内容属于单独、明确的破坏性确认，不能由后台清理触发。

## 10. 文件、资料就绪与上传恢复

文件任务与业务记录分别确认：本地文件已保存不代表已上传，资产 ready 不代表照片说明已同步，旅行资料已同步不代表选择的文件已下载。

- 本地选取文件先复制到原账号私有持久目录、完成写入并计算校验信息，再在数据库事务登记 file_task、稳定 asset_id 及相关操作。文件系统与数据库不是一个事务：先完成不可变文件，再提交引用；提交失败仅产生可辨认的孤立文件，恢复清理只能删没有任何操作/任务引用的孤立副本，不能先删原文件。
- file_task 至少保存 local_file_id、owner、用途、尺寸/摘要、稳定 asset_id/asset.register operation_id、目标记录、阶段、upload_attempt、可恢复偏移（能力支持时）、错误与下次重试时间。签名 URL/密钥不进入业务操作或同步日志；过期授权重新申请。不同内容需新 asset_id，不能用同 ID 替换 ready 文件。
- 上传阶段为 local_saved、waiting_registration、waiting_upload、uploading、processing、ready、failed；缺网络暂停，不把进程被杀后的 uploading 当 ready。先经 asset.register 注册元数据，依赖此操作的 photo/document/票据引用可在上传前保存，沿用服务端允许引用 uploading/processing/failed 资产的语义。字节上传/确认使用现有联网接口和 upload_attempt；每次重启从持久任务与服务器资产状态恢复。
- 服务端确认后只进入 processing，服务器校验通过才 ready；ETag、摘要/大小/类型校验继续使用既有 worker。失败可续签或重新上传同内容，不重复新建业务记录。缩略图和原图状态分别处理。大文件断点仅在 H03/H14 验证协议、对象存储和系统能力后启用；不支持时从头重传保留同业务标识，不能承诺强停后后台持续运行。
- 下载阶段为 queued、downloading、verifying、ready、failed；字节写临时文件，校验预期大小/摘要后原子替换，并将完成元数据落库；缺摘要时须取得服务端可验证信息后才标记完整，不只检查文件存在。ready 只指选择的 variant，缓存缩略图不能冒充原图已下载。引用资产失效/账号不匹配时拒绝展示新下载内容。
- 旅行离线状态分别维护 `details_state` 与 `files_state`，明确所选附件范围。只有完整详情基线和后续变更已处理、所选文件全部校验完成，才能显示相应“离线就绪”；未选择文件不暗中下载全量原图。同步冲突和待上传数量作为独立状态保留。

## 11. AI 本地操作与确认

模型地址、模型名及密钥由用户配置；凭据只在本机系统安全存储，不进入旅行同步、崩溃日志或普通偏好导出。请求由应用直接连接配置的模型服务，不经 Tripfolio 后端代理；默认不包含全量旅行、原始附件、其他账号资料或密钥。界面说明模型接收方及本次必要数据范围，网络失败保留输入和本地结果，不虚报执行。

- 查询通过本地只读业务接口，返回账号/旅行范围、完整程度、local_revision、待同步/冲突状态和资料确认时间。模型回复必须区分本地计划与服务器确认，资料未下载时说明缺失，不能臆造今天的行程。调用远端模型需要网络，不将“本地读写”描述为模型可离线运行。
- 首版 AI 写工具只覆盖旅行、行程、账目、行李清单与待办的本地业务操作；分类/成员可查询供引用，其管理不默认开放给 AI。不能修改账号安全、分享、永久删除、服务器配置、模型密钥、任意文件或数据库。工具名与参数只能映射到第 3 节的允许子集；资料文本/模型输出不是用户授权。
- 模型给出意图后先通过 preview 校验，显示新增/修改/删除数量、具体内容、金额/币种/付款分摊、删除影响、待补地点和文件状态。用户明确确认前不产生业务覆盖或队列；批量预览必须说明“本地保存可原子，服务器按操作同步，可能部分成功”。
- 预览令牌保存在本机，绑定原账号、确认批次 ID、可见变更集合、涉及实体/集合的 local_revision、epoch 与稳定拟操作 ID。确认时在同一事务重新核对所有读取依赖；任何依赖变化或切号、过期预览均返回 PREVIEW_STALE，重新预览并确认，不能暗中扩大范围。
- 重复点击、AI 重试和进程重启使用同一已确认批次 ID，命中本地持久回执，不重复入队。确认失败事务不保留半份操作；成功后模型再次要求“重试”不能生成新的同意记录。模型后续新增行为需要新的预览/确认。
- 应用逐项展示本地已保存、待同步、已确认、冲突/失败；依赖失败不会显示整批完成。可撤销操作按第 9 节生成补偿或撤销尚未发送命令，重新校验最新基线；永久删除不作为撤销实现，已上传文件的垃圾回收仍由引用与生命周期决定。

H04 文档验收要求：全部产品离线范围有明确命令或本地草稿规则；版本/依赖/去重/批次/基线相互一致；风险和未验证项可定位；场景矩阵能由后续任务执行。H04 完成不代表 H06 等任务的其他前置解除，也不代表 v2 可立即启用。

服务器发布 v2 前必须完成以下门槛：

1. 由协调会话另行分配并实施 OpenAPI/生成契约、数据库迁移和业务适配；本文仅定义要求，不在本任务修改这些文件。schema 迁移采用增量迁移，历史收据/日志/未同步数据不删除；packing/todo 排序、稳定自有成员 ID、关联 guard、收据元数据及 epoch 是明确新增点。
2. 全部同步相关写路径产出 schema_version=2 的可解释事件；初次 v2 基线在迁移完成后捕获 H，客户端不从旧同步文档的游标启动。后续出现旧 schema 事件必须有经过验证的无损转换，否则要求重建基线并暂停受影响应用，不能静默丢字段。新增 schema/实体需协商升级，不能继续用2掩盖不兼容改动。
3. 当前 Web 与服务器按第4节部署 guard，并验证 v2 账号所有敏感写入口的强制检查；未达到此门槛时 status 不向该账号宣告可用v2。旧客户端读取和无关写入可继续，缺基线的敏感操作明确拒绝并保留用户输入，不牺牲新版并发安全换取静默兼容。
4. C01～C18、C27～C32 中相应服务端场景具备真实证据，H10 完成首个端到端闭环后才扩展核心离线业务。账号级启用应先完成 baseline；失败可暂停新推送但保留已写收据/日志、客户端覆盖和队列，不回滚schema或清空本地状态。
