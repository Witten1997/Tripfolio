# 单二进制部署设计

2026-09-15 起，后端只交付**一个可执行文件**：前端构建产物嵌入其中，HTTP 服务与后台任务同进程运行，启动时自动完成数据库迁移。本文记录这个决定、进程模型与部署约束。

## 1. 为什么合并

原来的部署形态是「Go API + Go worker + Caddy + 迁移二进制 + 前端产物」四五个部件，靠 Compose 串起来。对个人项目来说运维面太大：Caddy 要为静态资源、反向代理、高德安全密钥代理单独维护一份配置，前端产物要靠卷挂载，迁移要靠独立的 init 容器。合并后的收益：

- 部署物只有二进制与一份 `.env`，容器镜像只有一个进程。
- 静态资源、SPA 回退、高德安全密钥代理都在进程内完成，**不再需要 Caddy**，也不会出现两处代理配置漂移。
- 迁移与代码同一次编译产出，不存在「新二进制配旧迁移」。
- 前端与后端版本天然一致：换前端必须重新编译，这正是期望的行为。

代价：改一行前端也要重编译二进制（几秒）；API 与 worker 同生共死；前端构建期变量（`VITE_AMAP_JS_KEY`）在编译时固定，换 Key 要重新打包。

## 2. 进程模型

```text
tripfolio serve
  ├─ 1. 读取 .env 与环境变量，校验配置
  ├─ 2. 等待 PostgreSQL 可达（可配置超时，默认 60s，带进度日志）
  ├─ 3. 自动迁移（River 自有表 → 业务表，会话锁串行）；TRIPFOLIO_AUTO_MIGRATE=false 可跳过
  ├─ 4. 装配服务（连接池、仓储、对象存储、高德、邮件）
  ├─ 5. 启动 River worker（消费资产校验、缩略图、清理等任务）
  └─ 6. 启动 HTTP 服务（/api/v1、/health/*、内嵌前端、/_AMapService）
```

退出时先停 HTTP（在途请求走完），再停 worker（在 `TRIPFOLIO_SHUTDOWN_TIMEOUT` 内等在途任务结束）。

保留子命令：`migrate up|status|down`（发布流程或排障单独跑迁移）、`healthcheck`（容器健康检查）、`version`。

## 3. 静态资源与高德代理

- 前端产物通过 `go:embed all:dist` 嵌入 `internal/web/dist/`。仓库里提交占位 `.gitignore`（embed 要求目录至少有一个文件，因此没有构建前端时 `go build ./...`、`go test ./...` 依然可用），打包脚本把 `apps/client/dist` 复制进去后再编译；缺少入口文件时页面返回一页说明，接口不受影响。
- `/assets/*`：命中则返回，带 `Cache-Control: public, max-age=31536000, immutable`（文件名含内容哈希）；未命中返回 404，不回落成 HTML。
- 其他路径：命中文件直接返回（`no-cache`），否则返回 `index.html`（`no-cache`），支撑前端路由。**以点开头的路径一律 404**：`all:dist` 会把 `.gitignore` 这类构建期文件也嵌进来，它们不该通过 HTTP 暴露。
- `/api/v1/*` 与 `/health/*` 优先匹配，未匹配的才进入静态处理，因此接口 404 仍是 problem+json。
- `/_AMapService/*`：进程内反向代理到高德三个官方域名（代理在构造时预建，请求路径上不重复解析上游地址），服务端**覆盖**请求里的 `jscode`（保留其余查询参数），安全密钥用 `TRIPFOLIO_AMAP_JSCODE` 提供，不进入浏览器产物。未配置该变量时代理返回 503 并说明原因，页面仍可用只是没有底图。
- 文本响应统一走 chi 的压缩中间件做 gzip（JSON、HTML、JS、CSS 等）：单二进制不再有 Caddy 承担这一层，高德返回的二进制瓦片不在压缩类型表内，已是压缩编码的响应会跳过。

## 4. HTTPS 与反向代理

二进制只监听 HTTP（`TRIPFOLIO_HTTP_ADDR`，默认 `:8080`），**不内置证书**。需要 HTTPS 时在前面放一层已有的 Nginx / Caddy / 云负载均衡，转发 `/`、`/api/*`、`/health/*` 与 `/_AMapService/*` 到该端口即可，无额外配置。此时 `TRIPFOLIO_WEB_BASE_URL` 填对外域名，`TRIPFOLIO_CORS_ORIGINS` 填网页域与 Capacitor 来源。

纯 http 部署（内网、个人服务器）不需要任何额外开关：`TRIPFOLIO_WEB_BASE_URL` 写 `http://…` 即可启动，刷新 Cookie 的 `Secure` **自动跟随站点协议**（http 关闭、https 开启），启动日志里打印一条告警说明代价——分享链接是 http、刷新 Cookie 不以 Secure 传输、Cookie 名不带 `__Host-` 前缀。这样处理而不是拒绝启动，是因为自托管环境里纯 http 很常见，把「没有 TLS」当成配置错误只会把人挡在门外；真正需要强调的是取舍本身，所以用告警而不是错误。需要 HTTPS 时在前面放一层 Nginx / Caddy / 云负载均衡即可，把地址改成 https 后 `Secure` 会自动恢复。

纯 http 还有一个只会在这里出现的坑：**非安全上下文**。浏览器只在 HTTPS 或 localhost 下提供 `crypto.randomUUID`、`navigator.clipboard` 与 `crypto.subtle`，`http://<域名或内网 IP>:<端口>` 三者都没有。`crypto.randomUUID` 缺失尤其隐蔽——注册、登录、创建旅行、新建分类与行程项目、更新资料、上传资产都要用它生成 UUID 与 `Idempotency-Key`，它一抛 `TypeError`，请求**还没发出去**就失败，页面只显示「网络错误，请稍后再试」，服务端日志里连这条请求都看不到。因此前端对这些能力一律做降级，而不是假定安全上下文：

- UUID 走 `src/shared/randomId.ts`：优先 `crypto.randomUUID`，缺失时用同样不受安全上下文限制的 `crypto.getRandomValues` 自行拼 v4（不用 `Math.random`）。
- 复制走平台层 `web/clipboard.ts`：优先 `navigator.clipboard`，缺失时退回 `document.execCommand('copy')`，两者都不可用才提示手动复制。
- `crypto.subtle` 缺失时跳过文件摘要（`assets.ts`），上传本身不受影响。

`localhost` 与 `127.0.0.1` 属于安全上下文，所以本机开发不会暴露这些差异；同一份代码放到 `http://192.168.1.10:8080` 就会。要判定当前页面是不是安全上下文，在控制台看 `isSecureContext` 即可。

## 5. 外部依赖

- **PostgreSQL**：沿用已有实例，不随部署再起一个。要求：**PostgreSQL 13 及以上**（开发与 CI 用 18；迁移与查询不使用 15+ 专有语法，13/14 同样可跑）、库已创建、用户能建表（迁移需要 `CREATE TABLE`/`ALTER TABLE`/`CREATE INDEX`）、连接串可被容器网络访问。迁移只用标准 SQL，不依赖任何扩展。
- **对象存储**：生产用阿里云 OSS（或任何 S3 兼容服务）。端点必须是**浏览器能直接访问**的地址，因为上传是前端拿服务端签发的授权直传；OSS 需在控制台为桶配置 CORS（允许 `PUT/GET/HEAD`、暴露 `ETag`、来源填网页域）。
- **邮件**：注册与找回密码的验证码走 SMTP，生产不允许 `log` 驱动。

## 6. 启动失败的可诊断性

部署后最常见的问题是「容器起来就退出」。因此启动流程做了三件事：

1. **阶段化日志**：每一步都先打印「正在做什么」（JSON 日志带 `phase` 字段），失败时能看到卡在哪一步。
2. **失败块**：启动失败时向 stderr 打印固定的中文块——阶段、原因、以及这一阶段的排查清单（例如数据库连不上会提示检查连接串主机名、网络、账号权限）。日志级别调到 `error` 也不会丢。
3. **退出码区分阶段**：`2` 配置、`3` 数据库、`4` 迁移、`5` 装配与后台任务、`6` HTTP 监听，便于脚本与运维快速判断。

后台任务的启动单独做了两层处理，因为它的失败原因与「装配」完全不同（2026-09-16 补）：

- **重试**：River 拉取队列设置的超时是它内部写死的 10 秒（`producer.StartWorkContext`），而这一步是对 `river_queue` 的 `INSERT ... ON CONFLICT (name) DO UPDATE`——远端或跨网数据库抖动一下、或被同一行的行锁挡住一会儿，单次尝试就会失败。容器因此退出再重启的代价远大于原地重试，所以启动任务消费默认重试 3 次（间隔 2s、4s），中途收到退出信号立即停止重试。
- **现场取证**：重试都失败后，进程会在给出建议前先探测数据库（往返耗时、以及其它会话里有没有长时间未提交的事务），把结果写进失败块。这样「数据库其实很健康，是别的事务占着锁」与「数据库本身连不上/很慢」在 stderr 上就是两句话的区别，不需要再去猜。

数据库等待与迁移失败都会带原始错误，不吞掉底层原因；排障对照表见 `docker/README.md`。

## 7. 容器与发布

`docker/` 下三件东西：`Dockerfile`（前端构建 → 嵌入 → 编译单二进制 → alpine 运行镜像）、`docker-compose.yaml`（只有一个应用服务，连外部 PostgreSQL 与 OSS）、`.env.example`（变量模板）。

发布流程：`docker compose build` → `.env` 填好外部依赖 → `docker compose up -d`。容器启动即自动迁移，不需要单独的迁移步骤；回滚用镜像标签，迁移只前进不回退（`migrate down` 仅供开发）。

前端构建期变量（`VITE_AMAP_JS_KEY`，以及跨域部署才需要的 `VITE_API_BASE_URL`）在编译时固定，改值必须重新 build 镜像。可选变量一律「不传」而不是「传空串」：空串会覆盖前端的默认值——客户端已把前缀解析改成 `||` 并加了回归测试，但保持「不传」才是原意。

健康检查由镜像的 `HEALTHCHECK` 提供（`/app/tripfolio healthcheck` 请求本机 `/health/ready`），compose 不重复定义；需要调整间隔时在部署侧覆盖。

## 8. 边界

- 单副本假设不变：分享限流与高德缓存是进程内状态，横向扩容前需改为共享存储，并让所有副本使用同一份 `TRIPFOLIO_KEYRING`。
- 内置静态资源意味着二进制体积随前端产物增长（当前约 2 MB 左右 gzip 后的产物）。
- 不再提供容器内的 Caddy：压缩已由进程内的中间件承担，其余边缘功能（TLS、WAF、限流、灰度）放在外层代理。
