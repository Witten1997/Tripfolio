## 3. 数据语义

- 一个账号拥有多趟旅行；旅行内容及其关联必须属于同一账号、同一旅行。账号 ID 从认证上下文取得。
- 每趟旅行只有一个记账币种，默认 CNY。存在有效账目时币种锁定（CURRENCY_LOCKED），有效账目数归零时自动解锁；无账目但已有总预算或预计费用时需先清空这些金额（CURRENCY_AMOUNTS_EXIST）。锁定与解锁都递增旅行版本并写入变更流。
- 地点坐标统一使用高德的 GCJ-02 坐标系。设备定位得到的 WGS-84 坐标以及照片 EXIF 中的坐标，由客户端经高德 SDK 或坐标转换服务转换后再提交。逆地理编码与地点搜索经服务端代理调用高德 Web 服务 API，密钥不下发客户端，结果不落库。
- 金额用十进制字符串传输、NUMERIC(18,4) 存储。服务端按币种的小数位校验，拒绝多余精度，不依靠数据库自动舍入。
- 支出和退款都输入正数；类型决定统计符号。账单分类是账号级可管理实体，注册时种入六个预设，跨旅行共用；有未删除账目引用的分类不能删除。
- 账号级实体（目前只有账单分类）同样有版本并进入同步流，其变更的 trip_id 为空，客户端始终保留；其他业务实体都归属具体旅行。行程项目与账目、待办、预订、照片之间不建立关联。
- 旅行日期、账目日期、待办截止日使用 date。计划和实际安排使用不带偏移的当地日期时间，并按旅行唯一的 IANA 时区解释；系统创建时间与过期时间使用 timestamptz。P0 不自动处理同一旅行中多个时区的换算。
- 旅行阶段按当前日期与起止日期计算；归档是独立状态。计划外日期只提示，不截断已有行程或排除旅前、旅后账目。
- 所有公开资源使用 UUID；离线新增的 ID 由客户端生成。版本和同步序列为 bigint，JSON 中使用字符串。
- 文件字节放私有对象存储；数据库保存对象键及元数据，临时签名地址不入业务表或同步日志。

## 4. 统一写入与同步

### 4.1 写事务

1. 验证身份，以 READ COMMITTED 开启事务，第一条语句 SELECT ... FOR UPDATE 锁定该账号的 account_sync_state 行；确认账号可写。
2. 按账号和 operation_id 查 mutation_receipts，比较规范化请求指纹（规则见接口设计 1.2）。成功重试返回原操作结果，并按 primary 的 ID 重新读取当前资源填充 data，不再用旧版本校验或再次写入。
3. 新操作校验旅行可写状态、资源归属、关联和业务规则；检查实体是否已删除或其 ID 已被使用。版本校验按 4.2 的字段级合并规则：删除、动作和整体替换要求版本相等；局部更新在基线之后的变更字段与本次提交字段不相交时合并应用，否则冲突。成功重试不因目标后来进入回收站而重新执行这些校验。
4. 修改业务行及关联，递增受影响资源的版本。票据关联通过账目版本维护，总预算随旅行版本维护。
5. 为每个变化资源分配连续同步序列，写入白名单快照或删除标记，并记录该版本实际变化的字段列表 changed_fields；同一事务的日志标记同一 batch_id 和 batch_end_seq。
6. 保存不含业务正文的操作结果；如需后台工作，使用 River 的事务入队接口一同提交。任何失败整体回滚。

账号内的同步写入按此锁串行，账号之间并行。锁纪律：可同步写事务只使用 READ COMMITTED，因为 REPEATABLE READ 下等待该行锁会以序列化失败告终而不是排队；取锁必须是事务第一条语句；锁内不执行循环批处理，重排与模板应用等多行操作受单次请求上限约束，永久删除等后台清理每批单独取锁并提交；连接统一设置 lock_timeout 与 statement_timeout；锁内不调用邮件、对象存储或图片处理服务。注册、令牌刷新等安全操作不写旅行同步日志；注销状态切换也要与账号写锁协调。

普通 REST 与同步推送调用同一业务入口。跨模块修改由 workflow 在一个事务中组织，不逐个调用会自行提交的服务。

### 4.2 增量同步

- 游标是不透明、签名且绑定账号的值，包含协议版本与已扫描序列；不能使用设备时间或普通自增主键替代提交顺序。
- 一轮拉取首先固定已提交的上界；分页仅读取此上界以内的数据，返回 next_cursor、has_more。结束后以该上界开始下一轮。
- 页面可能切开同一变更批次。客户端先将页面持久化到暂存区，收齐 batch_end_seq 对应批次后，才在本地事务中应用该批次；不能把半个批次当作已完成。
- 客户端按资源版本应用数据，旧版本不能覆盖新版本。文件元数据同步不代表文件已下载。
- 变更日志建议保留 90 天。只有完整批次可以过期清理；游标早于保留边界时返回 CURSOR_EXPIRED，进入快照核对流程。
- 推送限于账目新增/编辑，以及物资和待办状态变化。P0 不开放离线删除、行程编排、预算修改、预订修改、分类管理或文件上传。
- 批量推送逐操作提交、逐操作返回结果；失败不会撤销此前已成功的独立操作。后续依赖操作返回 dependency_failed。
- 更新操作携带基线版本。服务端读取基线之后各版本的 changed_fields 并求并集，与本次提交字段不相交时直接应用（版本递增，warnings 返回 MERGED_WITH_NEWER_VERSION）；相交、所需日志已过期或目标已删除时才返回冲突。物资状态与待办完成状态的同步操作不带基线版本，最后写入生效并递增版本。
- 冲突返回服务端版本、当前内容与 conflicting_fields；客户端保留原始基线和未提交修改。用户采用自己的内容时，基于最新版本生成新的 operation_id，不使用强制覆盖参数。
- 操作入队后内容不可修改，重试原样重发，服务端以 replayed 结果作答，这就是“查询重试结果”的方式。离线新建实体的版本链是确定的：创建后版本为 1，本设备后续每次更新加 1，直到收到其他设备对该实体的变更；客户端据此填写后续更新的基线版本，不猜测其他值。

### 4.3 快照与离线范围

快照使用 data_snapshots + snapshot_items 保存短期、不可变的白名单记录。worker 在一个有超时和容量限制的 REPEATABLE READ 事务内，第一条语句普通读取 account_sync_state.last_seq 作为上界（不加锁），随后读取业务行、写入快照行和 snapshot_asset_refs。由于变更序列在账号写锁内分配并与业务行同事务提交，该事务快照中可见的业务行与 seq <= 上界的变更严格对应，不需要与业务写入互斥，快照构建期间该账号的写入不被阻塞。

快照与文件回收、永久删除的竞争不依赖锁：普通回收只处理无引用满 24 小时的资产，而快照 24 小时过期且只引用当时被业务记录引用的资产，两者在时间上不重叠；永久删除会物理删除 assets 行，snapshot_asset_refs → assets 的外键使删除在存在活动快照引用时失败，清理任务重新执行“撤销受影响快照”步骤后重试；快照事务插入引用时若行已被删除同样失败并整体重试。提交后再提供分页下载；网络下载和文件打包不占用此数据库事务。

- baseline 快照包含账号级账单分类、全部旅行的基础信息，以及用户选定旅行的当前有效详细数据；回收站仅包含旅行基础信息。
- trip_reload 快照用于新增离线旅行或恢复旅行后的重新下载；它不会推进已有账号级同步游标。
- 增量流保持账号级、不按旅行过滤。客户端保留账号级实体和全部旅行的基础信息，只保留已选择旅行的详细数据；其他详细变更扫描后可以丢弃。
- 新选择旅行时，用 trip_reload 补齐当时状态，再继续处理增量流；较旧的事件由版本比较忽略。
- baseline 只在完整核对后把游标推进到快照上界。未同步操作及其基线先单独保存，再叠加到新基线或标记冲突，不清空用户输入。
- 快照建议 24 小时过期；导出快照仅供后台任务读取。永久删除涉及的快照立即失效，再清除其内容。

### 4.4 删除与防重放

- 旅行删除先置 deleted_at，建议 30 天内可恢复；子记录保留，通过父旅行的状态统一隐藏。
- trip 删除事件表示本地整趟旅行退出可用集合。恢复发出新版本的 trip 事件并标记 requires_snapshot，所选离线旅行重新拉取详细数据。
- 单个业务记录软删除后不提供独立回收站，30 天后可清理正文。行程项目与其他记录之间没有外键关联，删除或跳过项目只修改本行；删除预订时同事务将其资料的 reservation_id 置空并递增资料版本，资料保留为独立资料。
- 永久删除先使目标不可访问，撤销受影响快照和导出下载资格，然后异步清理关联和对象。清理分批执行，每批在账号写锁内完成并单独提交；删除 assets 行前必须先使引用它的活动快照失效并删除其引用，遇到外键失败时重新执行该步骤。同步历史中的相关正文也要清除。
- 对被清除正文的历史变更，保留原序列位置并以 redacted 标记返回，不携带快照；删除/清理的最终标记仍可被客户端读取。redacted 只推进扫描进度，不恢复或覆盖实体。
- 物理删除前，在 entity_tombstones 留下账号、资源类型、ID、最后版本等无正文标记。旧 ID 不能重新创建；旧设备编辑返回 RESOURCE_GONE。
- mutation_receipts 的成功结果只保存资源标识、版本、游标及警告代码，不保存账目、笔记、邮箱或请求正文。它与轻量墓碑保留至账号注销，防止日志过期后重试再次记账。

## 5. 文件、导出与注销

### 5.1 文件生命周期

创建 asset 时一并登记首次上传尝试，并直接返回仅能写暂存对象的短期授权；上传尝试作为 assets 的一组列维护，每个资产同一时刻只有一个活动尝试，重试递增尝试序号并使用新的暂存键。确认请求只登记处理任务；worker 校验真实大小、文件类型和摘要，以校验时读取到的对象 ETag 为条件执行服务端复制（阿里云 OSS 的 x-oss-copy-source-if-match、S3 的 CopySourceIfMatch）到客户端不可写的最终对象键，ETag 不匹配即判定失败并要求重新上传；再标记 ready。缩略图按后台任务处理。

旧上传授权不会覆盖已确认的最终文件；已 ready 的资产不再签发上传授权，替换文件需新建资产再更换引用。

documents、photos、ledger_attachments 和账号头像分别建立具体引用。引用可以在资产上传完成前建立：资产只需属于同一账号（旅行文件还必须属于同一旅行）且未被删除，状态可为 uploading、processing、ready 或 failed；下载、缩略图和导出只对 ready 资产有效。引用先于字节存在，上传中与失败状态因此能跨设备、跨刷新保留，失败后在同一资产上创建新尝试重试。解除一个引用不会删除其他引用正在使用的文件。无引用文件建议等待 24 小时再回收，活动快照的引用也参与保留判断。

照片记录先于文件字节保存；上传失败不丢失已填写的说明。浏览器文件类型和大小仅作提示，服务端重新验证。初始建议：单图 20 MiB，PDF 50 MiB；上传授权 5 分钟，确认窗口 30 分钟；下载授权原图与 PDF 60 秒、缩略图 15 分钟，支持一次为最多 100 个资产批量签发。

### 5.2 导出

- 支持旅行 ZIP 数据包和账目 CSV，可选择全部有效旅行或指定旅行；默认排除回收站。
- 以 worker 建立快照的时间为数据截止点，界面展示该时间，后续修改不混入本次导出。
- ZIP 包含 manifest.json、版本化业务 JSON 和文件；不含密码、令牌、验证码、同步内部表或签名地址。
- CSV 包含旅行名称、币种、支出/退款类型、发生日期、分类、金额和备注；表格公式前缀做安全转义。
- ZIP 只打包 ready 资产的文件；被引用但处于 uploading、processing 或 failed 状态的资产在 manifest.json 中按引用列为 unavailable 并注明状态，不阻塞导出。ready 资产的对象缺失属于数据不一致，任务明确失败，不将缺件的包标记为完整成功。CSV 不因照片未上传而失败。
- 导出包建议保留 7 天；下载地址由授权接口在有效访问令牌下校验归属后签发，有效 60 秒，不要求密码复验。
- 永久删除旅行或注销账号，会撤销包含这些资料的已有导出下载并删除相应导出对象，避免副本留存。

### 5.3 账号注销

用户先验证当前密码，使会话获得 5 分钟内有效的近期认证状态，再提交明确的注销确认。账号转为 deleting，阻止常规读写和新登录。清理任务先撤销文件和导出下载资格，再分阶段删除对象及数据库数据，所有步骤可重试。

提交时返回只允许查询该注销任务的随机 receipt_token，服务端仅保留哈希；注销过程中及完成后，用户可凭此凭证查询进度。它不能访问旅行数据，也不能取消或重复执行清理。任务完成后删除账号和凭证数据；任务的最小状态记录及 receipt_token 哈希再保留 7 天，随后删除。

对象存储中已签发地址最迟在其短期有效期结束后失效，不能承诺即时撤回已下载内容。成功注销要求应用控制的对象和数据库内容已清理；生产备份按独立的备份保留策略到期清除。

## 6. 实现验收重点

| 场景 | 应验证的结果 |
| --- | --- |
| 相同 operation_id 重试记账 | 返回原写入结果，不产生第二笔账目 |
| 相同 operation_id 使用不同内容 | IDEMPOTENCY_CONFLICT，无新增变更 |
| 两端基于同一旧版本编辑相交字段 | 后到操作冲突，附 conflicting_fields，保留用户未提交内容 |
| 两端基于同一旧版本编辑不相交字段 | 后到操作合并应用，版本递增，warnings 含 MERGED_WITH_NEWER_VERSION |
| 账号 A 引用账号 B 的 ID | 查询不泄露存在性，写入被拒绝，复合外键也不能跨账号关联 |
| 跨旅行附加文件或退款关联 | 被拒绝，不产生悬空或错属关系 |
| 记账成功但响应丢失 | REST 与同步重试都可获取同一成功结果 |
| 写事务回滚 | 业务、变更日志、收据与 River 入队一起回滚 |
| 同一批次分成多个同步页面 | 客户端收齐后再应用，无中间关联缺失 |
| 日志过期且本地仍有修改 | 全量核对后仍保留待同步内容 |
| 旅行删除、恢复和永久清理 | 正确隐藏或重新下载；旧离线编辑不能复活被删除数据 |
| 删除后重放很早的创建请求 | 成功收据或墓碑阻止重建 |
| 无引用文件回收、导出并发 | 活动引用不会被提前清理；永久删除使相关快照和导出失效 |
| 统计跨越旅前与旅后日期 | 默认包含全部关联账目，净支出和分类口径一致 |
| 删除有关联退款的支出 | 退款保留并转为独立退款，warnings 含 REFUNDS_UNLINKED |
| 刷新令牌响应丢失后用旧令牌重试 | 宽限期内签发新令牌对，不撤销会话；宽限期外视为复用并撤销 |
| 快照构建期间业务写入 | 写入不被阻塞；快照内容与其上界一致 |
| 上传中或失败的照片 | 照片记录及资产状态跨设备可见，可在同一资产上重试，说明不丢失 |
| 删除有未删除账目引用的分类 | 409 CATEGORY_IN_USE，无变更 |
| 账号级分类变更 | trip_id 为空的变更进入增量流与 baseline，所有客户端保留 |
| 批量加入物品库条目 | 一个事务写入，同分类同名与请求内重复项跳过并在响应列出 |
| 同步操作瞬时失败 | 逐操作结果 status=failed、retryable=true，原样重试后得到 applied 或 replayed |

以上为设计验收要求，本轮尚无服务代码、迁移执行或运行测试结果。
